# 災難備援與備份政策 (DR & Backup Policy)

> **用途**：確保資料安全與業務連續性
> **適用範圍**：全公司 IT 系統
> **文件版本**：v1.0

---

## 一、備份原則

### 3-2-1 備份原則

| 原則 | 說明 | 本組織實作 |
|------|------|-----------|
| **3** 份備份 | 原始資料 + 本地備份 + 異地備份 | ✅ |
| **2** 種不同媒體 | 不只用同一種儲存裝置 | ✅ SSD + 雲端儲存 |
| **1** 份異地備份 | 與生產環境不同地理位置 | ✅ AWS S3 / Azure Blob |

### 備份類型定義

| 類型 | 說明 | 保留週期 |
|------|------|----------|
| 每日增量備份 | 只備份當日變更的資料 | 30 天 |
| 每週完整備份 | 完整系統備份 | 12 週 |
| 每月完整備份 | 完整系統備份 | 12 個月 |
| 每年封存備份 | 法規遵循用 | 7 年 |

## 二、各系統備份規範

### 資料庫

| 系統 | 備份方式 | 排程 | 保留策略 | 還原目標 (RTO) | 復原點目標 (RPO) |
|------|----------|------|----------|----------------|------------------|
| MySQL / MariaDB | mysqldump + binlog | 每日 full + 每 5 分鐘 binlog | 30 天 | 2 小時 | 5 分鐘 |
| PostgreSQL | pg_dump + WAL | 每日 full + 每 15 分 WAL | 30 天 | 2 小時 | 15 分鐘 |
| MongoDB | mongodump + Oplog | 每日 full + 每小時增量 | 14 天 | 4 小時 | 1 小時 |
| Redis | RDB + AOF | 每小時 RDB | 7 天 | 1 小時 | 5 分鐘 |

### 應用程式與配置

| 項目 | 備份方式 | 排程 | 保留策略 | RTO |
|------|----------|------|----------|-----|
| 原始碼 | Git (自動 push) | 每次 Commit | 永久 | 30 分鐘 |
| 容器 Image | Registry (Docker Hub / ECR) | 每次 Build | 保留最新 50 版 | 30 分鐘 |
| K8S Manifest | GitOps (Flux / ArgoCD) | 每次變更 | 永久（Git 歷史） | 30 分鐘 |
| 系統配置 (/etc, nginx.conf) | Ansible + Git | 每次變更 | 永久 | 1 小時 |
| 環境變數 / Secret | Vault / Sealed Secrets | 每次變更 | 永久 | 1 小時 |

### 雲端資源

| 項目 | 備份方式 | 排程 | 保留策略 |
|------|----------|------|----------|
| AWS EC2 | AMI + Snapshot | 每週 AMI + 每日 Snapshot | 保留 4 份 AMI |
| AWS RDS | 自動 Snapshot | 每日 + 每 30 分鐘 transaction log | 保留 35 天 |
| AWS S3 | Cross-Region Replication | 即時同步 | 永久 |
| AWS EBS | Snapshot | 每日 | 保留 30 天 |
|  Terraform State | S3 + DynamoDB Lock | 每次 apply | 永久 |

## 三、災難備援計畫 (DR Plan)

### 災難分級

| 等級 | 定義 | 範例 | DR 目標 |
|------|------|------|---------|
| L1 | 單一服務異常 | 某個 API 掛掉 | RTO < 2hr |
| L2 | 單一可用區故障 | AWS AZ 掛掉 | RTO < 4hr |
| L3 | 單一 Region 故障 | AWS us-east-1 全掛 | RTO < 8hr |
| L4 | 多 Region 故障 / 機房全毀 | 天災、戰爭 | RTO < 24hr |

### DR 策略（依系統等級）

| 系統等級 | 範例 | DR 策略 | RTO | RPO |
|----------|------|---------|-----|-----|
| **Tier 0 - Mission Critical** | 官網、交易系統、核心 DB | Active-Active 多活 | < 15 分鐘 | < 1 分鐘 |
| **Tier 1 - Business Critical** | ERP、CRM、API | Active-Standby（Hot Standby） | < 1 小時 | < 15 分鐘 |
| **Tier 2 - Important** | 內部系統、Wiki、CI/CD | Warm Standby | < 4 小時 | < 1 小時 |
| **Tier 3 - Non-Critical** | 測試環境、開發環境 | Cold Standby（從備份重建） | < 24 小時 | < 24 小時 |

### DR 演練計畫

| 演練項目 | 頻率 | 參與人員 | 預期產出 |
|----------|------|----------|----------|
| DB 還原演練 | 每月 | DBA + SRE | 還原報告 |
| 備份完整性檢查 | 每週 | SRE | 備份檢查紀錄 |
| 切換演練（Staging） | 每季 | 全團隊 | DR 演練報告 |
| 完整災難切換（Prod→DR） | 每年 | 全團隊 + 管理層 | 改善建議清單 |

## 四、備份驗證

> 備份沒驗證 = 沒備份

| 檢查項目 | 頻率 | 驗證方式 | 負責人 |
|----------|------|----------|--------|
| 備份檔案完整性 | 每日 | md5 checksum | SRE |
| 備份檔案是否可讀 | 每週 | `tar -t` / `mysql -e "SELECT 1"` | SRE |
| 完整還原測試 | 每月 | 在 Staging 環境完整還原 | DBA |
| 異地備份可存取性 | 每週 | AWS CLI `ls` 檢查 | SRE |

## 五、緊急應變流程

### 系統異常 → 備份還原流程

```
異常發生
    ↓
值班人員確認問題等級
    ↓
判定需還原備份 → 通報主管
    ↓
確認備份時間點
    ↓
執行還原（先 Staging 驗證）
    ↓
驗證資料正確性
    ↓
切換至還原後的系統
    ↓
Post-mortem / RCA
```

## 六、備份架構圖（建議）

```
生產環境 (Primary Region)
    ├── 每日自動備份 ──→ S3 Standard (本地)
    ├── 即時 WAL/Log ──→ S3 Standard-IA
    └── 異地複寫 ──────→ S3 異地 Region (DR)
                            │
                            ↓
災難發生時 ──→ 從異地 S3 還原 ──→ DR Region 啟動服務
```
