# SRE / DevOps 統一文件與溝通標準建立指南

> **用途**：建立 SRE 與 DevOps 團隊的標準化文件體系與溝通語言，減少資訊落差、加速故障排除、提升維運品質
> **適用範圍**：維運部 / SRE / DevOps / 開發團隊
> **文件版本**：v1.0

---

## 一、為什麼需要統一文件標準？

### 痛點

| # | 問題 | 影響 |
|---|------|------|
| 1 | 事件發生時大家各自記錄，格式不一 | 事後 RCA 難以追蹤、根本原因難以收斂 |
| 2 | 變更沒有標準申請流程 | 變更失敗找不到負責人、回滾步驟遺失 |
| 3 | SOP 散落在工程師個人筆記 | 新人 onboarding 慢、關鍵操作只有特定人會 |
| 4 | 技術人員對 PM/主管講不清楚 | 跨部門溝通成本高、決策延誤 |
| 5 | 系統交接只靠口頭 | 人員異動時知識斷層、系統變成黑盒子 |

### 目標

- **統一格式**：所有維運文件使用相同模板，降低閱讀負擔
- **加速回應**：標準化 Incident 流程使 MTTR 可衡量、可改善
- **知識留存**：SOP、KT、架構文件不再存在個人腦中
- **跨部門溝通**：技術白話對照表讓 PM 與主管聽得懂
- **新人快速上手**：標準化訓練計畫與文件清單

## 三、導入步驟

### Phase 1：建立（第 1-2 週）

| 步驟 | 行動 | 產出 |
|------|------|------|
| 1.1 | 下載 10 份模板，依組織名稱客製化 | 客製化模板 |
| 1.2 | 確定文件存放位置（Git Repo / Wiki / Share） | 文件路徑 |
| 1.3 | 定義文件編號規則（INC-2026-001、CR-2026-001…） | 編號規則 |
| 1.4 | 設定模板存取權限 | 權限矩陣 |

### Phase 2：推動（第 3-4 週）

| 步驟 | 行動 | 負責人 |
|------|------|--------|
| 2.1 | 團隊教育訓練：說明模板用途與填寫方式 | 維運主管 |
| 2.2 | 建立 Incident 流程：事件發生必須填寫 01 模板 | 值班工程師 |
| 2.3 | 建立 Change 流程：任何變更必須填寫 02 模板 | 申請人 |
| 2.4 | 建立 SOP 撰寫文化：重複操作超過 3 次就寫 SOP | SRE / DevOps |

### Phase 3：驗收（第 5-6 週）

| 步驟 | 行動 | 檢查標準 |
|------|------|----------|
| 3.1 | 模擬 P1 事件，驗證 Incident + Change 流程 | 30 分鐘內完成通報 |
| 3.2 | 檢視模板填寫品質 | 欄位完整率 > 80% |
| 3.3 | 新人實際使用訓練計畫 | 4 週可獨立值班 |
| 3.4 | 跨部門簡報使用溝通對照表 | PM 回饋「聽得懂」 |

### Phase 4：持續改善

- **每季**：Review 所有模板的有效性，更新已過時內容
- **每年**：DR 演練 + 新人訓練計畫更新
- **事件後**：每次 P1/P2 事件後檢討模板是否需要修正

## 四、文件撰寫原則

### 4.1 黃金圈法則

| 層次 | 問題 | 範例 |
|------|------|------|
| Why | 為什麼要做？ | 避免服務中斷 |
| How | 怎麼做？ | 執行備份還原步驟 1-5 |
| What | 做了什麼？ | 已還原至 2026-05-27 08:00 |

### 4.2 STAR 原則（Incident Report）

| 元素 | 說明 |
|------|------|
| **S**ituation | 當時什麼情況 |
| **T**ask | 需要解決什麼 |
| **A**ction | 採取了什麼行動 |
| **R**esult | 結果如何 |

### 4.3 五個必問 (5 Whys)

寫 RCA 時連續問五次「為什麼」，直到找到根本原因：

```
問題：官網 502
Why 1：API 伺服器沒有回應
Why 2：資料庫連線數滿了
Why 3：某個慢查詢佔住連線不釋放
Why 4：該查詢沒有索引
Why 5：Code Review 沒有要求檢查 SQL 效能 ← 根本原因
```

### 4.4 白話文原則

> 寫給「明天早上的自己」看得懂，而不是寫給大神看的

| 不要寫 | 要寫 |
|--------|------|
| Pod 在 CrashLoopBackOff，kubectl describe 看到 OOMKilled | 系統因記憶體不足異常重啟 |
| 因為 SSL cert expiry 導致 TLS handshake failed | 網站安全憑證到期，使用者看到不安全警告 |
| DB Connection Pool Full，JDBC connection timeout | 資料庫連線數爆滿，無法處理新請求 |

### 版本管理規則

| 元素 | 規則 |
|------|------|
| 模板本身 | 使用 Git 版本控制，每次修改需 MR / PR |

| 版本號 | v1.0 → 小幅更新 v1.1 → 重大更新 v2.0 |

## 六、溝通標準

### 團隊內部（SRE / DevOps）

- **Slack**：`#incident`（事件通報）、`#changes`（變更通知）、`#ops`（日常討論）
- **值班交接**：每天 10:00 站會，交接 incident / change / 注意事項
- **文件優先**：能寫成文件的就不開會，能開短會的不開長會

### 跨部門（PM / 主管）

- **Incident 通報**：先說影響（官網掛了）再說原因（DB 問題），最後說時程（預計 30 分恢復）
- **變更申請**：提前 24 小時通知，用 CR 模板填寫，避免口頭請求
- **週報**：使用 05 模板，重點放「事件/變更/風險/改善」，避免技術細節

### 對高階主管簡報（口訣）

> **狀況 → 影響 → 解法 → 時程**

```
「這個系統異常影響了官網約 15 分鐘（狀況+影響），
原因是資料庫連線數異常升高（原因），
我們已經調整設定並增加監控告警（解法），
預計明天前完成根本改善（時程）。」
```

- [ ] 10 份模板已客製化並存放於共用位置

- [ ] 新人訓練計畫是否需要調整
