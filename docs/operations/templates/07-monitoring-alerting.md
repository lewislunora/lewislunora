# 監控與告警分級標準

> **用途**：統一監控項目、告警規則與處理流程
> **適用範圍**：維運部 / SRE / DevOps
> **文件版本**：v1.0

---

## 一、監控層級架構

```
┌─────────────────────────────────────────────┐
│          Layer 4: 商業指標監控                 │
│   訂單量、註冊數、交易成功率、營收              │
├─────────────────────────────────────────────┤
│          Layer 3: 應用程式監控 (APM)          │
│   API Latency、Error Rate、Throughput、DB    │
│    Query Performance、Slow Transaction       │
├─────────────────────────────────────────────┤
│          Layer 2: 基礎設施監控                 │
│   CPU、Memory、Disk、Network、Pod Status     │
│   Node Health、Container Restart             │
├─────────────────────────────────────────────┤
│          Layer 1: 硬體監控                    │
│   Server Hardware、Switch、Firewall、Storage │
│   UPS、空調、機房環境                         │
└─────────────────────────────────────────────┘
```

## 三、告警規則標準

### 3.1 基礎設施告警

| 監控項目 | 告警條件 (Warning) | 告警條件 (Critical) | 檢查間隔 | 等級 |
|----------|-------------------|---------------------|----------|------|
| CPU 使用率 | > 80% 持續 5 分鐘 | > 90% 持續 5 分鐘 | 1 分鐘 | P2 / P3 |
| 記憶體使用率 | > 85% | > 95% | 1 分鐘 | P2 / P3 |
| 磁碟使用率 | > 75% | > 85% | 5 分鐘 | P3 / P2 |
| 磁碟 I/O | > 80% 持續 10 分鐘 | > 90% 持續 10 分鐘 | 5 分鐘 | P3 |
| 網路流量 | > 80% 頻寬 | > 95% 頻寬 | 1 分鐘 | P2 / P3 |
| Swap 使用率 | > 50% | > 80% | 5 分鐘 | P3 |
| Load Average | > CPU 核心數 x2 | > CPU 核心數 x4 | 1 分鐘 | P2 / P3 |

### 3.2 Kubernetes 告警

| 監控項目 | 告警條件 | 等級 |
|----------|---------|------|
| Pod CrashLoopBackOff | 出現即告警 | P2 |
| Pod Pending > 5 分鐘 | 無法排程 | P2 |
| Node NotReady | 節點異常 | P1 |
| OOMKilled | 容器記憶體不足 | P2 |
| Deployment 滾動更新停滯 | > 10 分鐘 | P2 |
| PersistentVolume 用量 | > 85% | P3 |
| HPA 達到最大副本 | 觸發即告警 | P3 |

### 3.3 應用程式告警

| 監控項目 | 告警條件 | 等級 |
|----------|---------|------|
| API 回應時間 | > 2 秒（P95）持續 5 分鐘 | P2 |
| API Error Rate | > 1% 持續 5 分鐘 | P2 |
| API Error Rate | > 5%（緊急） | P1 |
| HTTP 5xx 比例 | > 2% 持續 5 分鐘 | P2 |
| HTTP 4xx 比例異常升高 | 較平時 > 200% | P3 |
| SSL 憑證到期 | < 30 天 | P3 |
| SSL 憑證到期 | < 7 天 | P2 |

### 3.4 資料庫告警

| 監控項目 | 告警條件 (Warning) | 告警條件 (Critical) | 等級 |
|----------|-------------------|---------------------|------|
| 連線數 | > 80% Max Connections | > 90% Max Connections | P2 / P1 |
| 查詢延遲 (Slow Query) | > 1 秒 | > 5 秒 | P3 / P2 |
| Replication Lag | > 10 秒 | > 60 秒 | P2 / P1 |
| DB 容量 | > 75% | > 85% | P3 / P2 |
| 交易 Deadlock | 出現即告警 | - | P2 |
| Backup 失敗 | 備份未執行 | 連續 2 次失敗 | P2 / P1 |

### 3.5 外部監控

| 監控項目 | 告警條件 | 檢查間隔 | 等級 |
|----------|---------|----------|------|
| 對外網站可用性 | 狀態碼非 200 | 1 分鐘 | P1 |
| SSL 憑證有效性 | 憑證錯誤 / 即將到期 | 每小時 | P1 / P2 |
| DNS 解析 | 無法解析 | 5 分鐘 | P1 |
| API 端點 | 回應時間 > 5 秒 或 狀態碼非 2xx | 1 分鐘 | P1 / P2 |

## 四、告警分級與回應

| 等級 | 定義 | 通知方式 | 回應時間 | 處理流程 |
|------|------|----------|----------|----------|
| **P1** | 服務中斷、使用完全無法使用 | 電話 + Slack + SMS | 15 分鐘 | Incident Response Process |
| **P2** | 部分功能異常、效能顯著下降 | Slack + Email | 30 分鐘 | 值班工程師處理 |
| **P3** | 不影響使用者的後端異常 | Slack（非緊急頻道） | 4 小時 | 工作日處理 |
| **P4** | 資訊性通知、容量規劃 | Email / Dashboard | 24 小時 | 納入 backlog |

## 五、告警抑制規則

> 避免告警風暴（Alert Storm）

| 情況 | 處理方式 |
|------|----------|
| 同主機多指標同時告警 | 只發送最高等級的那一則 |
| 已知維護時段 | 維護窗口期間自動靜音 |
| 相依服務告警 | 下層服務異常時，上層服務告警自動抑制 |
| 同事件重複告警 | 5 分鐘內不重複發送相同告警 |

## 六、Dashboard 標準

每個系統至少需有以下 Dashboard：

| Dashboard | 內容 | 維護團隊 |
|-----------|------|----------|
| **系統總覽** | CPU、Memory、Disk、Network | SRE |
| **K8S 集群** | Node、Pod、Deployment、Service | SRE |
| **API 監控** | Latency、Error Rate、Throughput | 開發團隊 |
| **資料庫** | Connections、Slow Query、Replication | DBA / SRE |
| **業務指標** | 使用者數、訂單量、交易額（可選） | 開發團隊 |

## 七、告警規則管理流程

1. **新增規則** → DevOps/SRE 提出 → 主管審核 → 加入監控
2. **修改規則** → 值班人員可調整 Threshold → 需在變更記錄註明
3. **刪除規則** → 確認已無告警價值 → 主管核准
4. **定期檢討** → 每季 Review 一次告警規則有效性
